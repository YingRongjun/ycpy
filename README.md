# 瀛澈拼音（ycpy）

一个跑在 IBus 上的拼音输入法引擎，**不需要编译、不需要 root、不装任何第三方 pip 包**。

```
cxy            ->  程序员  陈兴瑜  常见于  产学研  磁效应 ...
chengxuyuan    ->  程序员
nihao          ->  你好
```

- **全拼 + 首字母两种输入**：全拼写全、首字母写快，混着写也能命中前缀；
- **联想输入**：按联想键（默认 `Ctrl+;`）根据刚上屏的词给出后续词，越用越贴合；
- **记忆用户高频词**：选过的词词频 +1，下次直接排到第一，落盘保存；
- **专业领域词库**：首选项里勾选 IT / 财经 / 法律 / 医学 / 饮食 / 汽车，
  该领域的词会被提到前面；
- **首选项对话框**：候选数量、中英切换快捷键、联想开关、领域词库等都能配，
  改完立即生效；
- **词典 50 万词条**（jieba 语料词频 + pypinyin 全量汉字读音 + 13 万条口语整句）；
- **引擎启动 0.05 秒**（索引用 marshal 缓存，字符串打包存储）。

**授权**：GPL-3.0-or-later。词典全部由 `tools/` 下的脚本从公开数据源构建，
不含任何手工编写内容；整句词频取自 rime-frost 的 `知频.txt`（GPL-3.0），
这一项决定了整体采用 GPL-3.0。逐个数据源的授权、义务，以及被排除的候选源
各自的实测失败原因，见 **[data/CREDITS.md](data/CREDITS.md)**。

## 一、安装

### deb 包（推荐）

从 [Releases](https://github.com/YingRongjun/ycpy/releases) 下 `ycpy_1.0.0_amd64.deb`：

```bash
sudo apt install ./ycpy_1.0.0_amd64.deb
ibus restart
```

装完**不需要注销重登**。然后设置 → 键盘 → 输入源 → ＋ → 其他语言 → 中文 →
**瀛澈拼音**。

> **改过引擎名之后要重新添加一次输入源。** ibus 引擎名（组件 XML 里的
> `<name>`）是 GNOME 输入源列表的 key。改名后旧的条目就成了悬空引用，
> 症状是「包装好了、ibus list-engine 也认得到，但输入源列表里没有」——
> 和组件 XML 非法时的症状**一模一样**。这时候查 XML 是白查，要查的是：
>
> ```bash
> gsettings get org.gnome.desktop.input-sources sources   # 引擎名对不对
> ```
>
> 改成新名字即可，或者直接在设置里删掉旧条目重新添加。

### 从源码跑

**仓库里不含词典数据**（30 MB 的生成产物，见[第七节](#七词典是怎么来的)），
所以 clone 之后要先构建：

```bash
git clone https://github.com/YingRongjun/ycpy.git
cd ycpy

# 1) 生成词典（带缓存，第一次需要联网，约几分钟）
python3 tools/build_dict.py          # 主词典 + 搭配表 + Unihan 分级
python3 tools/build_phrase_freq.py   # 口语整句词频
python3 tools/build_domain_dict.py   # 专业领域词表（可选，只影响勾选功能）

# 2) 打包并安装（需要 sudo）
sh tools/build_deb.sh
sudo apt install ./build/deb/ycpy_1.0.0_amd64.deb
ibus restart
```

三个脚本都支持 `--offline`（只用本地缓存重新生成）。

装完自检：

```bash
python3 tests/test_core.py   # 200 个离线单测，不需要词典数据，跑得快
python3 tools/e2e_test.py    # 走完整 D-Bus 链路，验证 cxy -> 程序员
./tools/e2e_isolated.sh      # 私有 daemon 上压测 8 遍，不干扰当前会话
```

> `e2e_test.py` 直接对引擎发 `ProcessKeyEvent`，走的是真实 daemon，会和
> **你正在进行的桌面输入共用同一条总线**——跑的时候别同时敲键盘。要反复
> 压测请用 `e2e_isolated.sh`。

> **为什么只保留 deb 这一条路？** 项目最早还有个 `install.sh` 走用户级安装
> （写 `~/.config/environment.d` + 用户组件目录 + 自启项，不用 sudo）。
> 开源前删掉了，两个原因：它只跑 `build_dict.py`，而运行期实际需要 **13** 个
> 数据文件，缺 9 个——包括 `ycpy-trad.txt`，**缺繁体字表意味着繁体字会涌到
> 候选前列**，那不是「降级」是错的；而且用户级组件目录那条路本身有老问题
> （ibus 1.5.x 不读用户组件目录，见[第六节](#六安装与排查)）。

## 二、用法

| 按键 | 作用 |
|---|---|
| `a`–`z` | 组字（边打边出候选） |
| `1`–`9` `0` | 选第 1~9 / 第 10 个候选 |
| `空格` | 选第一项 |
| `回车` | **原样上屏你敲的字母**（不上屏候选词） |
| `Tab` | 选下一个候选 |
| `-` `=` / `PageDown` `PageUp` / `↓` `↑` | 翻页 |
| `Ctrl`+`;` | 上屏当前词并进入**联想**；联想中按空格可连续选词，`Esc` 退出 |
| `左 Shift`（单按） | **中文 / 英文切换**（组字中会先把拼音上屏；英文模式下所有键直通） |
| `Backspace` | 组字中删一个拼音字符；预编辑已空时放给应用，删已上屏的文字 |
| `Esc` | 清空 / 退出联想 |
| `Ctrl`+某键 | 透传（留给切换输入法等快捷键） |
| `CapsLock` 锁着时按字母 | 直接出大写英文，**不组字、不弹候选窗**（CapsLock 相当于临时英文开关） |
| 按住 `Shift`+字母 | 同上，直接出大写英文；组字中会先把已组的拼音上屏 |

`ü` 用 `v` 打（`nv` = 女），也接受 `ü`。中英切换和联想键都可在首选项里改。

**回车是「落英文」，空格才是「选词」**——这是两种不同的意图：中文态下你敲的
字母**始终显示在光标处**，候选窗在它下面展开，即使一个候选都没有（比如敲
`vvv`）字母也留在屏幕上。所以回车把你敲的拼音原样落成英文，空格才上屏候选词。

回显的是**你实际敲进去的字母**，不是规范化之后加分隔符的串：敲 `chengxu`
显示 `chengxu`，不是 `cheng xu`。输入法不擅自改写你的输入。

### 打错字也能出词

前缀二分只认「你敲的是词拼音的前缀」。一旦前缀根本不成立——漏了元音、声母
不分、首字母里混进元音、音节没敲完——两次二分都返回空。而这些在实际输入里
非常常见，所以会退一步，按「你可能本来想敲什么」生成变体再查一遍：

| 你敲的 | 猜成 | 属于哪类错误 |
|---|---|---|
| `nhao` `nha` | `nihao` `niha` → 你好 | `n` 后面漏了元音 |
| `chxy` `chxuy` | `cxy` → 程序员 | 声母不分（ch / c） |
| `zhxy` `shxy` | `zxy` `sxy` | 声母不分（zh / z、sh / s） |
| `cxuy` `cxuyu` | `cxy` → 程序员 | 首字母串里混进了元音 |
| `chenxuyuan` | `chengxuyuan` → 程序员 | 音节没敲完（漏了 `g`） |

最后一类值得单说：`chen` 压根不是 `cheng` 的前缀，所以**再怎么调前缀都救不
回来**。这类「音节内少敲一个字母」只能靠音节补全表（`chen -> cheng`，模块
加载时算一次）。

有五条约束保证容错不会干扰正常输入：

1. **精确命中足够多时不去猜**——`cxy` 命中 104 条，说明敲得很准；`nha` 只命中
   1 条（南海岸），明显不是想要的，才值得再猜。阈值 `fuzzy_min_exact` 可调，
   调到 0 就是完全关掉；
2. **变体数量封顶**（`MAX_VARIANTS = 8`），不让候选组合爆炸；
3. **音节补全只在完全查不到时启用**，且**能干净切成音节的一律不许动**——
   `split_syllables` 判据。`nihao` 去完元音是 `nh`，同样是纯声母，可它拼得
   完全正确（`ni`+`hao`）；真正的判据是能不能切成音节；
4. **保留变体查询里的「完全命中」标记**。这一条很关键：`chxy` 猜成 `cxy`
   之后，「程序员」的首字母**正好**是 `cxy`，该拿的完全命中奖励必须照拿，
   否则猜对了也会被语料词频埋掉；
5. **猜出来的结果加 `W_FUZZY` 负分**，永远排在精确命中之后，但同一批里仍按
   词频和用户词频排序——所以你选过一次的词会浮上来。

实测代价（正常输入都在 0.4 ms 以内）：

```
nihao  0.045 ms   cxy  0.165 ms   chxuy  0.252 ms   chenxuyuan  0.345 ms
```

> **已知短板**：只敲 1 个字母时会明显变慢（`n` 约 18 ms、`ni` 约 4.5 ms）。
> 原因是前缀太短——`n` 在 38 万词里能前缀命中 8915 条，光二分出来再逐条打分
> 就要十几毫秒。这个开销与容错功能无关，是短前缀的固有问题；真要优化得给
> 索引加长度分桶或提前截断。

### 中文标点

中文态下把英文标点转成中文标点（`ycpy/punctuation.py`）：

```
, → ，    . → 。    ? → ？    ! → ！    ; → ；    : → ：
` → 、    ( → （    ) → ）    [ → 【    ] → 】
Shift+< → 《   Shift+> → 》   Shift+" → ”
^ → ……    _ → ——    $ → ￥    ~ → ～
```

三条行为约定：

- **组字中打标点会先上屏候选词**。打 `nihao,` 得到「你好，」而不是「nihao，」，
  不需要先按回车。
- **英文直通态不转换**，原样交给应用。
- **分号归给标点**，联想键因此改成 `Ctrl+;`（其他输入法也普遍用这个组合键）。
  老配置里仍是「无修饰分号」的会自动迁移，用户自己改过的不动。

### 裸 Shift 必须「单按」才切换中英

`?` 和 `!` 本身就要按 Shift。如果一按 Shift 就切换，用户根本打不出这两个标点。

所以裸 Shift 改成**延迟到松开才判定**：

1. 按下 Shift 时不切换，只记一个待办，并把 Shift 交给应用（大写要靠它）；
2. 期间按了**任何**别的键（大写字母、`?`、`!`、方向键、功能键）→ 取消待办，
   Shift 只是修饰符；
3. **只有 Shift 自己的抬起**才结算待办，没有按过别的键才切换。

还有一条更要紧的：**切换用的那一次 Shift，按下和抬起都必须透传给应用**。
按下返回 `False` 是为了应用能正常处理大写；如果抬起返回 `True` 把它吃掉，
客户端就只收到 Shift 按下、永远等不到抬起，之后每个字母都是大写。

> 这个 bug 最迷惑的地方是：**打开 CapsLock 时反而正常**，因为 X11 里
> `Shift + CapsLock` 恰好等于小写。于是「锁了 CapsLock 就好了」这个现象会把
> 人带偏，根本想不到是 Shift 的抬起被吞了。

### 候选窗的规则

输入法必须让用户随时看得见「我敲的东西去哪了」：

| 状态 | 候选窗 | 预编辑 |
|---|---|---|
| 组字中（含一个候选都没匹配上） | **一直显示** | 显示用户敲的原始字母 |
| 退格删到还剩字母 | 仍显示 | 同步缩短 |
| 退格删光了最后一个字母 | 关闭 | 清空 |
| 上屏 / Esc / 失焦 | 关闭 | 清空 |

早先的规则是「有候选才显示」，于是敲了不匹配的拼音（比如 `vvv`）字母还在、
候选窗却没了，看起来像输入法把输入吞了。

**一个候选都匹配不上时给高频词，而不是空窗口**：GNOME 收到空的 lookup table
根本不画候选框，用户看到的是「按了键但什么都没发生」，完全不知道输入法还
活着。所以这时返回语料最高频的**双字词**——窗口就一直在，而且这些词本身就
是有用的高频输入。只取双字词是有意的：单字高频榜前几名是「了是在和有的他不我
的人也为」这类虚词，拿来当候选没什么用。

`PREEDIT_FOCUS_MODE_LOCATION` 让预编辑锚定在光标处，而 GNOME 的候选窗正好从
光标位置弹出——两者叠在一起，视觉上就是「字母在候选窗的左上角」。
> ibus 协议本身没有「在候选窗内部留一块文本位」的字段，预编辑永远由**客户端**
> 渲染。所以这是 ibus 框架下能做到的最接近的效果，和 `ibus-libpinyin` 一致。

## 三、配置

有三条入口，都指向同一个 GTK3 对话框：

| 入口 | 靠什么实现 |
|---|---|
| 应用菜单「瀛澈拼音首选项」 | 直接运行 |
| 设置 → 键盘 → 输入源 → ycpy 右侧 ⋮ → 首选项 | `ibus-setup-ycpy.desktop` |
| 右上角输入法菜单 → 首选项… | 引擎上报 property |

```bash
ycpy-preferences          # 命令行直接打开
```

可配置项：

| 项目 | 说明 |
|---|---|
| 每页候选词数量 | 5 / 7 / 9 |
| 中文 / 英文切换 | 点按钮后按组合键重新绑定，默认左 Shift（按住不放不会连切） |
| 联想输入 | 开关 + 快捷键（默认 `Ctrl+;`） |
| 每次上屏后自动进入联想 | 默认关 |
| 学习我的用词 | 关闭后退化为纯语料排序 |
| 我的词频权重 | 滑块；越大则自己常用的词排得越前，0 = 完全按语料排序 |
| 容错阈值 | 滑块 0–60；精确命中少于这么多条时额外猜变体（`nha`→你好），0 = 只按字面匹配 |
| 专业领域词库 | 6 个勾选框：IT / 财经 / 法律 / 医学 / 饮食 / 汽车 |

配置存在 `~/.config/py-pinyin-ibus/config.json`。引擎盯着这个文件的
`st_mtime_ns`，**保存后下一次按键就生效，不需要重启输入法**。文件损坏或缺
字段会自动回落到默认值，不会让引擎起不来。

> **为什么「设置 → 键盘」那条路要专门的 .desktop 文件？**
> gnome-control-center 里是硬编码去找 `ibus-setup-<引擎名>.desktop` 这个文件名，
> 它**不读**组件 XML 里的 `<setup>` 字段（它读的引擎字段只有 name / longname /
> language / layout / textdomain）。所以光在 XML 里写 `<setup>` 不够，必须真的
> 装一个 `ibus-setup-ycpy.desktop`。

> **右上角菜单那条路**：GNOME Shell 的输入法菜单是写死的，只有「显示键盘布局」
> 和「键盘设置」，**没有 per-engine 的首选项项**——这是 GNOME 的设计。但它会把
> 引擎上报的 property 渲染成菜单项（拼音的全/半角开关就是这么来的），所以引擎
> 在 FocusIn 时上报一个「首选项…」property，点击后 daemon 回送 `PropertyActivate`。
>
> property 的 `type` 必须是 **`PROP_TYPE_NORMAL`(0)**。GNOME 按它决定画成什么：
> `0` 是普通可点项、`1` 是开关按钮（`PopupSwitchMenuItem`）、`3` 是子菜单。
> 容易踩的坑是 `1` 其实不是 MENU 而是 TOGGLE——填错就会显示成一个开关。

## 四、原理

### 匹配：两个有序索引 + 二分前缀

没有建 Trie。36.6 万词条如果按音节建 Trie，光节点就得几百 MB Python 内存；
而「全拼前缀」和「首字母前缀」天然是两次有序数组的二分查找，常驻内存只有几十 MB。

```
data/ycpy-dict.txt:  程序员 <TAB> 170 <TAB> cheng xu yuan

全拼索引:  chengxuyuan     -> 有序数组，二分出「所有以它开头的区间」
首字母索引: cxy            -> 同上
```

输入 `cxy` 时两路各查一次再合并去重，就同时覆盖了首字母和全拼两种风格。
命中后按下面的权重打分：

```
score = 语料词频
      + 完全命中奖励（全拼 25000 / 首字母 25000）
      + 用户词频 × 60000 × 覆盖率   ← 选过 1 次就压过几乎所有冷门词
      + 上下文二元组 × 90000
      + 音节数吻合 + 字数偏好
```

**候选池不能按词频截断。** `kuang` 精确命中 587 条，其中拼音正好是 `kuang`
的单字有 87 个。按语料词频排序后「框」落在第 65 位，而候选池原先只留 36 个——
于是「框」**连候选池都进不去**，翻完所有页都看不到。拼音完全相同的字之间，
唯一能区分的就是词频，而词频低的字（常用但很少单独成词，比如「框」）天然吃亏。
用户敲了完整准确的 `kuang`，这些字都是合法答案，能不能被翻到不该由语料词频决定。

代价可接受：池子从 36 涨到 104 条，`kuang` 打分只要 **0.7 ms**。

### 单字排序：三级信号

单字没有词频可依，需要叠信号。三条**量纲完全不同**的信号，划带互不重叠：

| 信号 | 来源 | 说明 |
|---|---|---|
| 语料字频 | hanziDB 的名次 | 主信号。映射用 **log**（不是线性也不是倒数，见下）|
| 字级常用度 | 《通用规范汉字表》分级 | **只加在单字上**，多字词的语料词频本来就是真实的词频 |
| 繁体标记 | Unihan 繁简对应 | **硬分区**，不靠压分数 |

几个必须记住的点：

- **《通用规范汉字表》分级衡量的是「字形规范化程度」，不是「使用频率」。**
  早先直接拿 T 值当分数用，结果「将/会/对/这/个」全被划到 T3（稀缺字），
  而「者/正/遮/框」反倒拿到 T1。更糟的是 **T1 内部所有字分数完全相同**——
  这个信号在真正需要区分的地方一点作用都没有。

- **字频映射必须用 log。** 线性：前 50 名全挤在 970~1000，彼此几乎分不开，
  而前 50 名恰恰是最需要区分的（的/一/是/在/有/个/这/中…）。倒数：前 10 名
  吃掉绝大部分量程，第 100 名之后全被压成个位数。log 正好落在「前几百名分得
  开、长尾不喧宾夺主」的尺度上。

- **兜底分必须和语料分完全不重叠。** 字频表只收 6500 字，字频表里查不到的
  字走 T 值兜底——而**兜底分是常数**。曾经 T2 兜底 250 分 ≡ 语料榜第 992 名，
  也就是说任何一个未被收录的二级字，都能压过榜上 992 名之后的全部常用字。
  修法不是继续调系数，而是**划带**：`[FREQ_MIN, 1000]` 归语料收录的字，
  `[0, FREQ_MIN)` 归所有没被收录的（`FREQ_MIN = 150`）。于是「语料里查得到」
  本身就成了最强的常用度信号。
  > `tests/test_core.py` 里 `test_bands_never_overlap` 遍历全部 6500+ 个字
  > 守住这个不变量，比逐个断言「泰 排在嬯 前面」更根本：以后任何新加的兜底
  > 分支只要不小心把分给高，就会在这里炸掉。

- **繁体要硬分区，不能只压分数。** 得分里 jieba 词频是主项，量级到 80 万，
  而字级常用度的权重只意味着几万——一个词频稍高的冷僻繁体字就会插到常用
  简体前面。所以排序键是 `(是否繁体, -分数)`：先分区、区内再按分数降序，
  与两边分数**完全无关**。繁体字本身不会被剔除，翻页仍然找得到。

- **识别繁体不能用「不在简体字频表里」这个判据**——那会把大量生僻简体字也算
  成繁体，而且简体常用字得分可能比它低。必须用 Unicode 官方的繁简对应，
  有个坑：两个字段**方向相反，只用一个会漏掉一半**
  （`kSimplifiedVariant` 的键是繁体，`kTraditionalVariant` 的键是简体、值是
  繁体）。合并后还得排除自映射（会→会、了→了），否则这些简体字会被误判。

- **码位判定必须从大到小**：基本区起点 U+4E00 比扩展 A 的 U+3400 **大**，
  先判 `cp >= EXT_A` 会把「为」（U+4E3A）误判成罕用字直接打死。

- **候选里不能有系统字体渲染不出来的字。** CJK 扩展 B 及以后（U+20000 以上）
  在绝大多数 Linux 桌面上没有字体，客户端渲染出来就是一个个豆腐块——`kuang`
  原本 104 个候选里有 **32 个**是这种。靠码位硬编码排除只是近似，所以用
  `fc-list :lang=zh charset` 问 fontconfig 要真实覆盖区间（实测 19 ms，缓存后
  2 ms），见 `ycpy/fontcov.py`。
  > **fontconfig 在这件事上会报错**：实测 `fc-list :charset=2b6ed` 报 65 款
  > 字体覆盖「𫛭」，但手工解析 `NotoSansCJK-Regular.ttc` 的 cmap 子表，里面
  > 根本没有这个字形——Noto 的 .ttc 把大量空位也登记进了 charset。所以
  > U+20000 以上一律**无条件排除**，不信 fontconfig。

- **拼音数据里的讹误读音必须过滤掉。** pypinyin 的 `pinyin_dict.json` 里
  「而」有两个读音 `ér, néng`，而 néng 在现实中根本不存在——建库时把多音字的
  所有读音都展开登记，于是敲 `ne` 就命中「而」。共 7,437 个这类讹误读音。
  判据是**有词证**：该读音是否在真实词里出现过。实测 1,661 个多音字通过，
  而「长」「重」「还」「地」「藏」「朝」「行」全部保留。
  > **关键细节**：证据必须取自各词的**首选读音**。若拿展开后的读音去统计，
  > 我们**自己生成的伪词**（如「而能」）会反过来证明「而 的 neng 是合法的」，
  > 循环论证，垃圾读音永远删不掉。

### 用户词频要按「输入覆盖率」打折

用户偏好是无价之宝，但**不能一刀切**。踩过的坑：用户高频打了 22 次「你好」，
于是只敲一个 `n` 时，「你好」以 `22 × 60000` 的分数压过所有候选，霸占第一位。

可 `n` 只有一个字母，而「你好」要 `n-i-h-a-o` 五个字母才写得完——`n` 顶多算它的
开头，不是一次可信的指名。所以用户词频按覆盖度缩放（`_coverage`，下限 0.35）：

```
score += user_weight × 用户次数 × (输入能划出的音节数 ÷ 词的音节数)
```

于是 `n` 时「你好」只拿到 35% 权重，`nihao` 时拿满——敲全了它才该浮上来。

> 这条约束也解释了一个看起来很夸张的数字：用户词频的打分 `learn` 一次就加
> 6 万，打 51 次是 **1.5M**，而整份语料最高频的词也只有 88 万。所以**收紧
> 候选集比调权重可靠得多**——权重压不住一个词「本来就躺在命中列表里」的情况。

### 只敲一个韵母时，候选里只该有单字

敲 `ni` 不该出现「你好」，敲 `yong` 不该出现「用户」。落到实现上就是
「音节数 ≤ 1」，因为拼音里每个音节恰好一个韵母。

有个坑：**不能去数字母里的元音个数**——`yong` 里的 `g` 是声母的一部分
（`ong` 是完整韵母），`lv`/`nv` 里的 `v` 是 `ü` 的替身。必须交给 `split_syllables`
按音节切。另外 `i`/`u`/`v`/`o` 是零声母韵母、切不开音节，要单独认这一类。

首字母输入（`cxy`、`zhguo`）**不限制**：它切不开音节，本身就是奔着词去的。

### 输入里打出来的元音，是有用的意图信号

首字母匹配只比声母，所以 `这个`(zhe ge) 和 `中国`(zhong guo) 在 `zg` 眼里
长得一模一样，全靠语料词频决胜负。但用户敲 `zhguo` 时把 `guo` 整个音节都打了
出来——这是明确的意图，不该被丢掉。于是首字母命中时，若候选拼音里也含这些
元音就加分（`W_VOWEL_MATCH`）。全拼命中不加分：那条路径本来就比过元音了。

### 长串拼音自动切成词拼成一句

敲 `dajiayiqiganhuo` 要能打出「大家一起干活」。

词库是**按词**存的——jieba 的 `dict.txt` 里只有「大家」「一起」「干活」，没有
它们的拼接。所以要新增一层「整句拼接」（`ycpy/segment.py`）：先切成音节，再按词
查，用打分模型挑切法。候选 = 一串词（一条切分路径），路径分是各词得分之和：

```
score(词) = log(词频) - log(音节数)
```

减去音节数就是按「每音节」归一化——**这一步是关键**。踩过的坑是「每音节频次 =
词频 / 字数」，那样算出来「到」是 20 万/音节、「大家」只有 0.95 万/音节，于是
永远选出「到+将+也+其+干+或」这种全单字串。用户要的是词，不是把每个音节都猜成
最常见的单字。

**必须用 k-best 动态规划，不能穷举。** 每段取 3 个候选词，12 个音节就是
3¹¹≈18 万条路径；实测 `dajiayiqiganhuo` 要 **4 秒**——每敲一个键等 4 秒是不能
接受的。改成从后往前算「位置 i 往后的最佳 K 条」，复杂度降到
O(音节数 × 段长 × K)，**62 毫秒**。保留 K>1 条是必要的：`yiqi` 该拼「一起」
还是「一切」，两者语料频次几乎相同（只差 0.03 nat）。

> **不要用「log 概率 × 大系数」表达语料偏好。** 本想让语料压住用户词频，把
> 系数调到 40000，结果 3.3 nat 的差距被放大成 13 万分，于是语料上**更差**的
> 切分拿到更高分。现在用「名次 + 原始 nat 值」两个维度。
>
> 用户词频在整句里要**大幅打折**（0.15）：用户选过「将」「好」，不代表他想打
> 「到将好」。

### 联想：三档信号 + 一层兜底

| 档位 | 来源 | 说明 |
|---|---|---|
| 1（最强） | 用户自己的输入历史 | 「程序员」后面你打过什么 |
| 2 | 语料搭配表 | 从 pypinyin 词组里切出来的「二字上下文 → 二字后继」|
| 3（兜底） | 字级二元组统计 | 上文末字常接哪些字 → 以该字开头的常用双字词 |
| 4（保底） | 词典按末字做文本前缀 | 前三层全落空时给点东西，而不是空窗口 |

前三档的量纲完全不同（次数 / 共现权重 / 权重×词频），直接混排没有意义，所以先
分档再在档内排序。用户历史永远压过静态统计——这就是「越用越准」的实现方式。

> 第 4 层是必需的：字级搭配表只收语料里最高频的 **2500 个字**，生僻字不在
> 其中。踩过的坑是选完「陈兴瑜」再按联想键，末字「瑜」查不到任何搭配，联想窗
> 就是个空的。

### 专业领域词库

主词典对专业词的覆盖极差（实测缺失率）：

```
法律 91.4%   饮食 88.9%   汽车 88.5%   IT 73.0%   医学 70.3%   财经 43.8%
```

所以接入 THUOCL 的 6 个领域词表，**按需加载成独立索引**。

**为什么是独立索引而不是并进主词典**——两个实测数据决定的：

```
Dictionary.add_user_words(9895 条)      36,848 ms   且没有 remove 方法
单独建一个小索引（同一批）                    24 ms   快 1549 倍
```

`Dictionary` **没有 remove / drop / reload**，一旦 `add_user_words` 灌进去就撤不
回来，用户「勾了又取消」根本没法处理。独立索引的生命周期完全独立：不勾选的文件
根本不读，取消勾选就是丢弃那个索引对象。而且**主词典的 marshal 缓存永远命中**，
不受勾选变化影响。

> 反过来说领域文件就不该进 `_cache_path()` 的键——**不参与建索引的文件，就不该
> 进缓存键**。（这是缓存键那条教训的反面：缓存键必须覆盖所有**参与建索引**的
> 文件。）

**DF 必须标定到 jieba 量纲。** THUOCL 给的是 DF（文档数），与语料词频不是一个
量纲（`版权` DF=1320 万 vs `的` freq=88 万）。用 14,103 个两表共有的词做 log
空间回归：

```
log(jieba_freq) = 0.3195 * log(DF) + 0.7154
```

保序性逐领域验证过，6 个领域近邻顺序一致率全 **100%**。

**领域加权必须是加性的，不能用「硬分区」把领域词排到前面。** 分区键只在一处
排序里生效，`score_with_context` 里第二处 `sort(key=-score)` 会把它整个抹掉，
而那里的二元组加权一次就 +9 万分。

**而且要看匹配质量。** `W_DOMAIN` 曾经是个不看匹配质量的固定加分，于是敲
`bianhua` 时，「变换规则」（只是前缀命中）拿到和「变化」（完全命中）一样的
15 万加权，再叠加长词加分反而更高——输入法就替用户决定了要「变换规则」。所以
按命中类型分档：

| 命中类型 | 含义 | 加权 |
|---|---|---|
| `full` | 全拼完整（`bianhua` → `bian hua`）| `W_DOMAIN` = 150000 |
| `init` | 韵母缩写完整（`sjk` → `shu ju ku`）| `W_DOMAIN` = 150000 |
| `pre` | 只是前缀（`bianhua` → `bian hua n...`）| `W_DOMAIN × 0.12` = 18000 |

领域索引同时维护全拼键和首字母键——敲 `sjk` 想打「数据库」时，那恰恰是用户主动
缩写之后的**明确意图**。

实测：

```
bianhua   变化 彼岸花 变化无穷 变换器 变换规则 变换中心   <- 「变化」第一
shujuku   数据库 数据块 数据库访问 数据库设计              <- 完整拼音仍优先
sjk       数据库 数据块 神经科 设计库                    <- 韵母缩写也优先
thpz      通货膨胀 通货膨胀率                            <- 同上
bianhu    辩护 便壶 扁壶 编户                            <- 前缀不参与领域优先
```

三个容易踩的顺序问题：

1. **领域词要在容错搜索之前问。** `xinkaiyue`（新凯越，汽车）只在领域索引里，
   主词典前缀查询 0 条。若先走容错搜索，它会给出「新开铺月」这类音节补全猜出来
   的垃圾，于是 `hits` 非空，后面那条 `if not hits` 不成立，领域词**永远没机会
   进池子**——勾了「汽车」却打不出任何汽车词。
2. **主词典已有的领域词要提权而不是跳过。** 「疾病」主词典 freq=4194，「肌病」
   主词典没有。最初的去重逻辑直接 `continue`，结果「疾病」一点分都加不上，
   被「肌病」压到第 4 位——用户勾了「医学」，最常见的那个医学词反而掉下去。
3. **不能重复计分。** 主词典那份已经算过 `W_EXACT_FULL`(25000) 和
   `W_SYL_COUNT`(2500)，领域侧若整条链重跑就凭空多出 27500。所以领域侧对主
   词典已有的词只做提权。

`W_DOMAIN = 150000` 的取值依据（实测多字候选的分数带 1016~156970，15 万略高于
「中国」的最高分，保证勾选后 `zhongguo` 时「中国银监会」能压过「中国人民解放军」）。
这个值同时满足「**用户词频 > 领域默认值**」：

```
「疾病」(2音节，输入jibing 2音节)        学 3 次 -> 180000 > 150000  ✅
「中国共产党」(4音节，输入zhongguo 2音节)  学 8 次 -> 240000 > 150000  ✅
```

后者要 8 次是因为只敲了一半输入——这与覆盖度设计的本意一致。

> 这两个值（`W_DOMAIN=150000` 和前缀比例 `0.12`）是**暂定的**，实际使用中如果
> 觉得领域词还是太靠前/不够靠前，直接改 `ycpy/composer.py` 顶部即可。

## 五、ibus 协议契约

这一节是全文最该读的部分。ibus 的按键模型有两个特性，**几乎所有难查的 bug 都
源于违反它们**：

1. **客户端按下、松开各送一次 `ProcessKeyEvent`**，ibus 用 modifier 的第 30 位
   区分（`IBUS_RELEASE_MASK = 1 << 30`）；
2. **引擎对松开不产生任何动作，只负责回放「这次按下当时返回了什么」。**

### 按下和松开必须给出一致的答案

引擎对松开一律返回「和按下一样的结论」。不一致的后果是客户端只收到一半事件、
它内部的按键状态机就停在「按下」，进而**自动重复**：

```
按一次数字，屏幕上连续输出一串同样的数字
按一次退格，一直往回删
凭空冒出好几个换行
```

> 所以 `process_key` 的结构是：见到 release mask 就回放 `_last_press_consumed`
> 而不是做任何动作；其余情况做正常处理并记下结论。
>
> **没有先按下过的孤立松开事件仍消费掉**，避免漏给应用。

### 每个键的抬起要回放**它自己**按下的结论

如果只留**一个**槽位，被**任何**键的按下覆盖，这个真实序列就出问题了：

```
Shift↓   引擎透传 → 槽位 False     应用看到 shift down
空格↓    组字态选词，被消费 → 槽位 True
空格↑    回放 True（对的）
Shift↑   回放槽位里的 True ← 这里回放的是**空格**的结论，不是 Shift 自己的
```

Shift 的抬起就这样被吃掉了。修饰键通常比它修饰的键**晚**抬起，所以 Shift / Ctrl
/ Alt 全都在这条路径上，最容易中招。而症状是「Shift 抬起不稳定，之后点鼠标变成
选中输入的文字」——因为客户端以为 Shift 还按着。

所以要**按 `keyval` 分别记录**，抬起时 `pop(keyval)`，一次 press/release 只配对
一次；没有配对按下的杂散抬起仍按老规矩消费掉。

### 「按下结论」记录要在焦点边界清空，但不能挪进 reset()

`ibus` 在切换窗口时确实会丢掉 release，这条路径上「没收到抬起」是真实存在的。
引擎侧修不了那个丢掉的 release（它根本没送到引擎），但能做的是**不让陈旧的记录
污染后续的抬起**——所以 `on_focus_out()` 里清空记录表。

**清理点必须放在 `on_focus_out()`，不能挪进 `reset()`。** 这是个反直觉但很硬的
约束：`reset()` 会在按键处理**内部**被调用（选词、退格清空、中英切换都会调），
那时用户完全可能正按住 Shift。把记录清掉，Shift 抬起时 `pop` 不到 → 兜底返回
`True` → 直接退化成上面那个「Shift 抬起被吞」的老 bug。焦点切换是唯一「可以确定
没有键还处于逻辑按下状态」的边界，所以清理只能放在那里。

### 但只清引擎自己吃掉的那些

清空记录表看起来解决了「没收到抬起」，却引入了更隐蔽的 bug：**记录里存的不只是
「引擎吃掉的键」，还有「透传给应用的键」，而后者必须留着**。

```
Backspace 按下  -> 返回 False -> 应用收到 press，开始删字
FocusOut 到达   -> clear() 把记录抹了
Backspace 抬起  -> pop 不到 -> 兜底返回 True -> 应用收不到 release
```

应用（GTK 一类）于是认为这个键**还按着**，开始自动重复。

**为什么它「偶尔」才出现**：X 会在同一时刻送出 KeyRelease 和 FocusOut，两者进
D-Bus 队列的先后不保证。只有焦点变化恰好落在「按下」与「抬起」之间的那个窄窗口
才会中招。

所以清理的正确写法是**只保留透传的那些**：

```python
self._press_consumed = {k: v for k, v in self._press_consumed.items() if not v}
```

`True` 的那些应用从头到尾没看见过，清掉或留着都无所谓；`False` 的留着，抬起才能
回放 `False`、和 press 配成完整的一对。

### 热键匹配必须忽略锁定状态位

客户端上报的 modifier 里**总是带着锁定键的当前状态**：NumLock、CapsLock、
ScrollLock 在 GDK 里分别是 `MOD2_MASK`、`LOCK_MASK`、`MOD5_MASK`。这些不是用户为
这个键按下的，不该参与匹配。

漏掉这条时，默认的中英切换键（左 Shift，无修饰）在真实客户端下**完全不起作用**：

```
配置：   {"keyval": 0xffe1, "modifiers": 0}     # 无修饰
客户端： keyval=0xffe1, modifier=16             # 16 = MOD2_MASK，即 NumLock
匹配：   want=0, got=16  ->  不命中
```

Shift 被当成普通键透传给应用。而 `Ctrl` / `Alt` 仍然参与匹配，它们是真正的组合键。

### 按键松开事件必须挡掉

`process_key` 开头就把 `modifier & IBUS_RELEASE_MASK` 消费掉且不做任何动作——
早期版本没区分按下和松开，于是按一个 `c` 就打出 `cc`。

### 预编辑为空时，退格要放给应用

退格有两种语义：预编辑里还有拼音时删拼音，预编辑空了之后就该删应用里已经上屏的
文字。引擎在预编辑为空时如果还 `return True`，这次按键就被吞掉，用户看到的就是
「退格键不工作」。

> 这类 bug 的排查线索常常指错方向：表现是「弹出候选窗」而不是安静地失效，更难
> 联想到退格头上。真实原因可能在**热键判定**里——早期 `_is_associate_key()` 的
> 条件写成「热键**是**分号」而不是「比 keyval」，于是命中默认配置时任何不带
> Ctrl/Alt 的键都被判成联想键，空格、回车、Tab、方向键全被一并劫持。

### CapsLock / 按住 Shift 时，字母直接出英文，不组字

字母只要带上 `LOCK_MASK` 或 `SHIFT_MASK`，就直接透传给应用出大写字母，**不进
组字、不弹候选窗**；组字中收到这种键，先把已组的拼音上屏，再让这个字母原样出去。

判定要同时看 `LOCK_MASK | SHIFT_MASK`，只看 Shift 的话 CapsLock 那条修不掉。
判定 CapsLock 状态时**别用「引擎有没有在组字」反推**——那个 `a` 自己会被组字收进
buffer，是自欺。要读事件 `modifier` 的 bit1（`LOCK_MASK`）。

### 真实客户端测不出来的东西

> **这一节所有 bug 有一个共同点**：单测和 e2e 都是手工构造 `modifier=0` 的
> 「纯按下」事件，所以它们**全都测不出来**。
>
> 教训是：真实客户端上报的 `modifier` 并不等于「用户按了哪些修饰键」，还带着
> 锁定状态位，而且按下和松开是两次独立调用。**凡是涉及 modifier 的逻辑，都必须
> 在真实 GTK 客户端里验证一遍**，光在 D-Bus 层手工构造事件会漏掉整类问题。

所以有了 `tools/stress_human.py` 这一层按人的速度的压测，见[第八节](#八工程)。

### D-Bus 序列化

ibus 引擎侧协议分两半：

- **daemon → 引擎**：普通方法调用，`ProcessKeyEvent`、`Reset`、`FocusIn`……
- **引擎 → daemon**：D-Bus 信号，`CommitText` / `UpdatePreeditText` /
  `UpdateLookupTable`，载荷是 ibus 自己的对象序列化格式。

最后这点最容易踩坑：`v` 类型里装的不是普通值，而是

```
IBusText        = ("IBusText", {}, 文本, IBusAttrList)     签名 sa{sv}sv
IBusLookupTable = ("IBusLookupTable", {}, page_size, cursor_pos,
                   cursor_visible, round, orientation, 候选数组, 标签数组)
                                                             签名 sa{sv}uubbiavav
```

也就是 `tuple(类名字符串, 父类字段…, 子类字段…)`。`ycpy/ibusproto.py` 手工拼了
这个结构，和 `ibus_serializable_serialize_object()` 的字节布局完全一致。

引擎本身不碰候选窗口——daemon 收到信号后会转给 `ibus-ui-gtk3` 或 gnome-shell。

### 启动脚本路径：两种安装布局都要找得到

`_script_path()` 要找 `ycpy-engine` / `ycpy-preferences`，而**两种布局下脚本位置
不一样**：

```
源码树   /opt/src/ycpy/ycpy-preferences     ← _ROOT 下
deb      /usr/lib/ycpy/       ← 只有 ycpy/ 和 data/，没有脚本
         /usr/bin/ycpy-preferences          ← 脚本在这
```

所以按顺序探测，而不是猜一个。踩过两次：第一次是 `dirname(_ROOT)` 把路径剥到了
上一层；「修好」时改成只找 `_ROOT` 下——源码树对了，deb 下又坏了。根因不是
「算错了」，是这个函数**从来没有同时兼顾过两种布局**，只测了源码树那一种。

> 配套的坑：`launch_preferences()` 里 `stderr=subprocess.DEVNULL` 而注释写着
> 「不能丢 stderr」——**注释和代码正好相反**，所以「点了没反应」查了两轮都无从
> 查起，子进程的 traceback 全进了 `/dev/null`。引擎进程常驻且没有终端，本来就
> 只能往 stderr 写，再关掉就彻底没线索了。

> **这类错误没法靠「点菜单」复现**——路径错时进程压根起不来，看着像「没反应」。
> 所以单测里直接断言路径存在且可执行（`ScriptPathTest`），而且**两种布局都测**。
>
> 顺带一提：Wayland 会话里对话框是 `GdkWaylandWindow`，不出现在 X11 的窗口树里，
> 用 `xwininfo` 查「窗口起没起来」会误判成没窗口。

### `delete-event` 必须返回单个 False

`lambda *_: (self._save(), False)` 这种写法本意是「先存盘、再让窗口关掉」，
但 `delete-event` **只有一个返回值**（gboolean），PyGObject 收到元组会按「多返回
值」去解包，GTK 那边拿到的就成了 `True`，而 `True` 的语义恰恰是「**阻止**默认
处理」——窗口于是根本不销毁。改成正常方法、返回单个 `False`。

> **测试上的坑**：想用 `win.emit("delete-event", None)` 验证，却发现返回 `False`
> 之后窗口照样还在，看着像没修好。其实是 **synthetic `emit()` 不跑 GTK 的类
> 闭包**。所以这里唯一可靠的信号就是返回值本身，断言也只断言返回值。

## 六、安装与排查

ibus 1.5.x 把用户组件目录 `~/.local/share/ibus/component` 在编译期用 `#if 0`
关掉了（`bus/registry.c` 的 `ibus_registry_load()` 只扫
`/usr/share/ibus/component`），而且**只在 daemon 启动时扫一次**。所以「把 XML
丢进用户目录就行」在这台机器上不成立。

**右上角图标**卡在同一个地方：gnome-shell 读的是 daemon 的 `Engines` 属性，而它
来自启动时扫描的注册表；自注册进去的引擎只会出现在 `ActiveEngines` 里，两边不是
同一份数据。所以光自注册，GNOME 根本「看不见」ycpy。

deb 包把组件装到 `/usr/share/ibus/component`，正好绕开这两点：

```
/usr/lib/ycpy/                       引擎代码 + 词典数据
/usr/share/ibus/component/ycpy.xml   ibus 组件描述（关键：系统目录才会被扫）
/usr/share/icons/hicolor/scalable/apps/ycpy.svg
/usr/bin/ycpy-engine                 薄包装 → python3 -m ycpy
/usr/bin/ycpy-preferences            薄包装 → python3 -m ycpy.preferences
```

构建：`sh tools/build_deb.sh`（不需要 root，用 `dpkg-deb --root-owner-group`
保证属主正确；打包后会**校验组件 XML 的合法性**，不合法直接中止构建）。

引擎侧仍保留**自注册**作为兜底（daemon 没扫到系统组件时的退路），启动时先检查
daemon 的 `Engines` 里有没有自己，有就跳过，避免同一个引擎注册两份、进而抢总线名。

> 这里有个必须遵守的约定——**注册必须由组件自己发起**，且要**先占住总线名并导出
> Factory，再注册**。daemon 会在调用方的连接上创建指向
> `/org/freedesktop/IBus/Factory` 的代理，并且 `destroy_with_factory` 为真；
> 如果这个连接上没人占着这个名字，代理会立刻销毁，注册也随之撤销。

进程入口是一个守护循环：ibus-daemon 随时可能重启（`ibus exit`、注销重登），引擎
靠 5 秒一次的 `Peer.Ping` 探测失联，然后重新找地址、重连、重新注册。

### 「列表里没有输入法」的定位顺序

**ibus-daemon 读到非法的组件文件时是静默跳过的**：不报错、不打日志、不进
`Engines`。于是症状只有「GNOME 的输入法列表里没有 ycpy」，看起来像安装没做对，
实际上文件从一开始就没被读过。

而这个症状**至少有四个成因**，按下面的顺序查：

```bash
# 1) 组件 XML 合法吗？（XML 注释内部不允许出现连续两个连字符）
python3 -c "import xml.etree.ElementTree as E; E.parse('/usr/share/ibus/component/ycpy.xml')"

# 2) daemon 真的读到了吗？
ibus list-engine | grep ycpy

# 3) GNOME 输入源列表里的引擎名对吗？（改名后最容易中招）
gsettings get org.gnome.desktop.input-sources sources

# 4) daemon 是不是刚重启过、注册表缓存没刷新？
#    ~/.cache/ibus/bus/registry 是组件注册表的缓存，
#    改了组件目录要删掉它或者重启 daemon 才会重新扫描
```

> 第 1 条真踩过：组件模板的注释里用了一个带双连字符的命令行选项来说明用法，
> 整个文件因此变成非法 XML，daemon 直接跳过。`data/ycpy.xml.in` 里那段注释现在
> 特意留了警示。

卸载策略：`dpkg -r` **保留**用户的词频学习数据（`~/.config/py-pinyin-ibus/`、
`~/.local/share/py-pinyin-ibus/`），升级输入法不该清掉长期积累的词库；真想彻底删
用 `dpkg -P ycpy`。

```

完整授权审计见 **[data/CREDITS.md](data/CREDITS.md)**，里面有每个源的授权义务、
被排除的候选源各自的实测失败原因，以及其它语料库为何补不上口语整句。

### 为什么需要整句词频表

jieba 词典**系统性不覆盖口语整句**：

```
输入 nihaoma -> 共 1 个候选：妳好吗

你好吗   不在
妳好吗   妳好吗 3 v     <- 频次 3，jieba 的默认兜底值
妳       妳 29 zg
你       你 234587 r
```

**一个频次 3 的边角异体词赢了 234587 的「你」**——之所以能赢，只是因为它的三音节
形式被收录了，而正确形式没有。「你好」(725) 在词典里，「你好吗」不在：词典只有拆开
的两条。凡是 jieba 没收录的整句，你唯一能拿到的候选就是它那些边角异体词的组合。

阈值 `MIN_FREQ=50` 是按「修好用户报的那些口语整句」倒推的：

| 阈值 | 条数 | 18 句常用口语能补上 |
|---|---|---|
| 20 | 286,807 | 17/18 |
| **50** | **133,770** | **17/18** |
| 100 | 70,625 | 16/18（漏「吃了吗」126、「你好啊」89）|
| 200 | 36,510 | 13/18（漏掉用户报的「你好吗」166）|

**换语料库解决不了**：需要的是*未经分词*的整句，而「你好吗」在任何分词后的语料里
都会被切成「你好」+「吗」。

> **两张表的词频不在同一个量纲上。** 知频的数值系统性偏大，直接混用会让
> `程序猿`(901) 压过 `程序员`(170)。用 246,096 个两表共有的词做 log 空间回归标定：
>
> ```
> log(jieba_freq) = 0.4932 * log(知频) + 0.6904
> ```
>
> 换算在 log 空间做（两表都是重尾分布，线性换算会让头部词爆掉），结果取整并夹在
> `>=1`。标定后「你好吗」排第一、「程序员」也回到第一。

> **分词重复产物**：上游是用 jieba 分词后统计的，所以会出现「同一个 token 连吐
> 两次」的产物（`对不起对不起` 词频 101 = 对不起 + 对不起）。判据是 `w == X+X`
> 且**要求整除**——这一条限制很关键，否则会误杀大量正常词（`仅仅是`、`往往会`、
> `慢慢的`、`谢谢你`）。代价是 `非常非常` 这类真叠词也会被剔掉，可以接受：打
> `非常非常` 时 `非常` 仍然是候选。

### 生成什么

| 文件 | 体积 | 内容 |
|---|---|---|
| `data/ycpy-dict.txt` | 11 MB | 词条、词频、读音（44.7 万行 / 36.6 万词条）|
| `data/ycpy-phrase-freq.txt` | 4.2 MB | 口语整句词频（13 万行）|

三个脚本都支持 `--offline`。缓存默认在 `~/.cache/ycpy-build/`（含下载的源包，

> API（`contents` 取 sha → `git/blobs` 取内容，>1 MB 只有 blob API 拿得到）。

### 性能

| 指标 | 数值 |
|---|---|
| 冷启动（重建索引） | ~4.5 s，只在词典文件变动后发生一次 |
| 启动（读缓存） | ~0.05 s |
| 常驻内存 | ~120 MB |
| 单次候选计算 | 0.1–0.6 ms（输入 1 个字母的最差情况约 56 ms） |

### 三层压测

| 脚本 | 速度 | 抓什么 |
|---|---|---|
| `stress_core.py` | 极快（故意不 sleep），5 小时 8 万条序列 / 220 万次按键 | 引擎内部状态错误 |
| `stress_human.py` | 按人的速度：按键间隔 90~280 ms、场景间停 0.4~2.5 s | **客户端收到了不该收到的键** |
| `e2e_isolated.sh` | 私有 daemon 跑端到端 | 真实 D-Bus 链路 |

`stress_core.py` 有个**结构性盲区**：**快到不真实的输入会制造出真人碰不到的状态，
也会掩盖真人会遇到的时序问题**。它永远不会出现这些：

- 按键之间 100~300 ms 的间隔（真人打字就是这个量级）；
- 按住不放的**自动重复**（X 连发 press、中间没有 release）；
- 焦点切换、鼠标点候选窗这类**异步事件插在按键中间**；
- 客户端与引擎之间 **D-Bus 往返的延迟**。

[第五节](#五ibus-协议契约)那个焦点竞态就是典型：窗口窄到只有人的节奏才撞得上，
`stress_core.py` 抓不到，`stress_human.py` 能抓到（后者专门有一个 `focus_race`
场景把 FocusOut 插在 press 与 release 之间）。

`stress_human.py` 的**核心不变量换了一个角度**——之前所有压测只验证「引擎内部状态
对不对」，但用户看到的现象是**客户端收到了不该收到的键**。所以它额外维护一个
**应用侧模型**：

- 引擎 `process_key` 返回 `False` = 这个键透传给应用；
- 返回 `True` = 引擎吃掉，应用看不到。

于是能精确断言：组字中回车/退格**必须**被吃掉；press 与 release 的结论**必须
一致**，否则客户端只收到一半、进而自动重复。

### 已知限制

- **不支持双拼、不支持模糊拼音**（`zh/z`、`ch/c`、`sh/s`、`n/l` 不等价）。
  想输「女士」要打 `nvshi` 或 `ns`，不会自动把 `nshi` 当成女。
- **中英混输**只在整词层面做——组字中途遇到非字母键，会把拼音原样上屏再放行该键，
  不会自动把已上屏的英文切换成中文。
- **不读 surrounding text**，联想的上下文只来自「通过本输入法上屏的词」。
  在别的输入法里打的字不会参与联想。
- **专业领域词库只在完整拼音或韵母缩写时优先**，前缀命中只给 12% 加权——
  这是用户明确要求的语义（用户只敲了 `bianhua`，输入法不该替他决定要「变换规则」）。
- 词库是 jieba 语料，缺少「程序员」这类较新的高频词时冷启动排序会偏冷门；
  选一次即可纠正。
- 词典文本不适合手动编辑，改动请改 `tools/` 下的脚本后重新生成。
